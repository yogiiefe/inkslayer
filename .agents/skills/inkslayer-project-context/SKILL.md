# INKSLAYER project context

## Workflow and implementation

Read root `AGENTS.md`, then only the relevant project documents: GDD for product behavior, LORE for canon, ARCHITECTURE for observed/proposed engineering, ROADMAP for milestone scope, and SKILLS for workflow ownership. Treat the code/build files as evidence of implementation. Documentation proposals are not proof that a system exists.

When planning a feature, state the player-visible outcome and the smallest playable slice that tests it. Trace dependencies through capture/recognition, teaching policy, spell command, combat, persistence and presentation as relevant. Select the owning skills from the inventory; do not load the entire catalog by default.

Keep handwriting recognition first in technical risk ordering. Prove recognition and beginner feedback before increasing mandatory Kanji content. Use the existing Java/libGDX stack and module boundaries unless the user requests a framework evaluation. Record design choices with rationale, affected systems, validation evidence and deferred decisions in the owning document.

## Best practices and anti-patterns

Preserve accepted text and append or edit only necessary sections. Keep skill instructions as reusable workflows and changing numbers/content in project data/docs. Avoid inventing Mr. Kotoba lore, equating task completion with gameplay delivery, silently changing scope to a web/other-engine game, or putting specialized algorithms in AGENTS.md.

## Validation and Definition of Done

Check that a plan names acceptance evidence, uncertainty and a cut list; check observed claims against actual files. For documentation changes verify relative links and distinguish confirmed/proposed/unimplemented states. Done means another session can locate the relevant workflow, understand the current milestone and identify remaining decisions without contradictory instructions.
